CASE STUDY 01 / CLOUD PIPELINE

Getting Oracle data onto a mainframe, reliably

Data in a modern Oracle database had to reach a mainframe that expects one specific file name, in the right order, every time. The first version worked until files got large and requests arrived together. The redesign has run stably in production and handles 10 GB per request.

ProblemDeliver Oracle data to a mainframe through Axway
StackSpring Batch, AWS Batch, S3, Lambda, SQS, EKS, Axway, Oracle
StatusStable in production, 10 GB per request

The goal

Data held in a modern Oracle database had to be put onto a mainframe. The route was to fetch the data, write it to a file, place the file in an S3 bucket, let a Lambda pick it up, and drop it into Axway, which transfers it to the mainframe.

MVP1: the first design

A Lambda watches the database for new requests and starts an AWS Batch job. The job runs Spring Batch, which fetches the data for a particular date. Spring Batch suited the work because all of that data had to be written into a file before it went to S3.

The file lands in an uploaded folder in S3, which triggers a Lambda event. The Lambda takes the file from there and places it in Axway. On success it moves the file from uploaded to transferred. If the Axway transfer fails, the file goes to a failed folder, so every file always has a clear status.

  1. Oracle DB
  2. Spring Batch on AWS Batch
  3. S3
  4. Lambda
  5. Axway
  6. Mainframe

Where it broke

Large files timed out

About one million records make roughly 1 GB. Lambda could transfer a file of that size, but anything above 2 or 3 GB failed on timeout. We tried streaming the file and using the smart_open library, and it still failed.

Race conditions on the Axway side

Files can have different names in S3, but the file dropped into Axway must always have the same name so the mainframe job recognises it. A Lambda starts a batch job whenever a request arrives, so when several requests came in together, jobs ran in parallel and tried to place files at once. The placement had to be put in sequence.

MVP2: the fixes

For the timeouts, I split the output in Spring Batch itself, into files of about one million records (around 1 GB) each. AWS Batch has no timeout limit like Lambda and offers several compute environment options, so the heavy work moved to where it fits.

For the race conditions, I introduced SQS so files are placed in Axway in sequence. The files still live in S3. The queue carries only each file’s name plus one piece of metadata that identifies the total number of files in that request.

I then built a dedicated EKS application to handle the large transfer instead of Lambda. It reads the SQS messages, takes the file names from them, pulls those files from S3 and places them in Axway.

MVP2 (changes highlighted)

  1. Oracle DB
  2. Spring Batch on AWS Batch: split files
  3. S3
  4. SQS: file names and metadata
  5. EKS transfer app
  6. Axway
  7. Mainframe

Files stay in S3. The queue carries only names and metadata, and the EKS app fetches each file from S3.

Outcome

MVP2 solved both problems and became stable in production. Where MVP1 started failing at 2 to 3 GB, the pipeline now handles 10 GB per request, split into about ten files of roughly 1 GB each.
