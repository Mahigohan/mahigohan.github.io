CASE STUDY 02 / RESILIENCE

Making a Kafka app on EKS resilient to failure

Normal retries alone didn’t make this Kafka app resilient. What helped was sorting errors into categories, giving each its own handling, and running a separate DLQ lane as its own deployment.

ServiceA Kafka app on EKS that processes messages and publishes downstream
StackJava, Spring Boot, Kafka, Amazon EKS, Avro
PatternThree error categories and a DLQ lane

The service

It’s a Spring Boot app running on EKS. It receives messages from producers, processes the data, and produces the results to a downstream consumer. Because it sits in the middle of other teams’ systems, how it behaves when something goes wrong matters as much as the happy path.

THE MAIN LANE

  1. Different producers
  2. Kafka input topic
  3. EKS consumer app
  4. Downstream topic

Why plain retries weren’t enough

Retrying every failure the same way did not solve the resiliency problem. Some errors never succeed on a retry, and some need more time than a short retry window allows. The fix was to separate the failures by type and give them a different lane.

Three kinds of failure

I split the exceptions into three categories, and used them to configure the Kafka consumer’s error handling. The configuration decides which errors are retried at the consumer level and which are acknowledged so the consumer can move on.

Non-retryable

Errors: anything a retry won’t fix, such as a null pointer exception.

Handling: the message is acknowledged and the consumer moves on. The failed message is stored in a database for analysis.

  1. Error raised
  2. Acknowledge
  3. Stored in DB for analysis
Retryable

Errors: failures that can clear on their own, such as connection problems.

Handling: retried at the consumer level, up to three times as configured. If it still fails after the retries, the message goes to the DLQ topic.

  1. Error raised
  2. Retry up to 3 times
  3. Still failing: DLQ topic
Direct DLQ

Errors: failures that need more than five or ten seconds to clear, where even exponential retries would still fail. Network delays are one example. Another is parallel transactions that take time to update, which behaves like a race condition.

Handling: sent straight to the DLQ topic, to be processed later.

  1. Error raised
  2. DLQ topic directly
  3. Processed later

The DLQ lane

I introduced the DLQ as a lane of its own, running as a separate deployment. It has no consumer-level retries. Instead, when a message in the DLQ fails again, the same message is put back on the DLQ, twice in total, and the retry count is configured in the DLQ’s Avro message.

That works because of who owns the payload. I can’t configure retries on the input topic, since the producers are different teams’ systems. DLQ messages are produced by the app itself, so it controls the payload and can carry its own retry settings.

THE DLQ LANE

  1. DLQ topic
  2. Separate DLQ deployment processes it
  3. Back to DLQ if it fails again, up to 2 times

What made the difference

Normal retries alone did not fix the resiliency problem. Segregating the exceptions into types, and giving failures a separate lane with its own deployment, did. The system became more resilient, and because each category ends up in its own place, issues are easier to identify.
